# 优化牌桌人机与结算

## Goal

修复本人公开组合越出玩家信息框的问题，提高人机对战中机器人的牌型演进和获胜能力，精简单局结算信息，并用回归测试锁定杠分与放赖倍率的独立规则。

## Background

- 本人的碰、杠组合当前没有显示在头像附近的玩家信息框内；其他三名玩家的公开组合展示正常。
- 人机模式中的机器人经常把刚摸到的牌原样打回，牌型长期不演进，导致大量流局。
- 单局结算上方重复展示倍率信息；用户只希望保留下方每名玩家的最终手牌、倍率、本局净变化和累计积分。
- 软胡基础倍率为 1×、硬胡基础倍率为 2×。每名玩家的个人倍率每局从 1× 开始，仅由放赖翻倍。
- 当前持久化使用 SQLite。本轮不实施 PostgreSQL 迁移；注册登录进入开发排期后再统一设计玩家主体、登录会话、名称、头像与 PostgreSQL 迁移。

## Requirements

### R1. 本人公开组合展示

- 本人的碰、明杠、暗杠、补杠和亮牌特殊碰杠必须与其他玩家一样，显示在头像、名称和分数所在的玩家信息框内部。
- 同一公开组合只能显示一次，不得在玩家信息框和底部手牌区域重复渲染。
- 最多四组公开组合时，组合仍受玩家信息框约束，不得越过信息框或牌桌可视区域。
- 保留现有碰/杠落地反馈、两套主题、横屏手机适配和减少动态效果设置。

### R2. 均衡拟人人机策略

- 机器人只能读取自己的暗牌和桌面公开信息，不得读取其他玩家暗牌或牌墙顺序。
- 机器人出牌必须评估成组、对子、搭子、孤张和仍可摸到的有效进张，不再固定优先打回本回合摸到的牌。
- 相近候选可使用可注入随机源打破平局，使行为不完全机械且测试可重放。
- 机器人可根据牌型收益决定碰、过和杠；可胡时应自摸，两张及以上赖子时应优先放赖至手中至多一张。
- 断线托管保持保守：响应阶段自动过，不使用完整机器人碰杠策略；主动阶段仍按既有规则自动胡、多赖子放赖和合法弃牌。
- 固定种子的多局模拟中，机器人必须能够实际胡牌，不得全部以流局结束；所有自动动作必须合法且牌局必须终止。

### R3. 精简单局结算

- 结算标题保留赢家与软/硬胡类型，或流局状态。
- 删除结算区域上方独立的倍率徽章、倍率公式和付款人倍率明细。
- 下方每名玩家仅展示最终暗手牌、个人倍率、本局净变化和累计积分。
- “本局”和“累计”必须有明确文字标签；本局净变化包含本局已经发生的杠分。
- 流局同样展示四名玩家的上述最终数据，并保留已产生的杠分变化。
- 人机模式继续提供“继续游戏”和“退出到主页”。

### R4. 杠分与个人倍率独立

- 软胡 1×、硬胡 2×规则保持不变。
- 每名玩家个人倍率每局从 1× 开始，每成功放出一张赖子翻倍；下一局重置为 1×。
- 普通碰不产生分数，也不修改任何玩家个人倍率。
- 明杠和亮牌特殊碰杠由对应弃牌者向操作者支付 3×底分。
- 暗杠由其他三家分别向操作者支付 2×底分。
- 补杠由其他三家分别向操作者支付 1×底分。
- 杠分即时、零和、与双方个人倍率无关；随后流局仍保留。
- 自摸付款继续按 `底分 × 软硬胡基础倍率 × 赢家个人倍率 × 付款人个人倍率` 计算。

### R5. 数据库决策

- 本轮继续使用现有 SQLite，不修改数据库驱动、部署或运行时数据格式。
- 后续注册登录开发前，应先拆分玩家主体与登录会话，确定名称同步语义，使用对象存储保存头像文件，再通过维护窗口迁移 PostgreSQL；不采用长期双写。

## Acceptance Criteria

- [ ] AC1：本人所有公开组合均位于本人玩家信息框内，最多四组时不越界且不重复渲染。
- [ ] AC2：桌面与 844×390 手机横屏、低调与精美两套主题均通过组合区域几何检查。
- [ ] AC3：机器人在“新摸牌能形成有效搭子、手中另有孤张”时不会机械打回新摸牌。
- [ ] AC4：机器人决策只消费自身暗牌与公开信息；BOT 与 TRUSTEE 自动响应行为有测试证明不同。
- [ ] AC5：固定种子多局模拟中的自动动作均合法、每局终止，且机器人至少能赢得部分对局。
- [ ] AC6：结算上方不再出现独立倍率徽章、公式或付款卡片；下方四行均展示最终手牌、倍率、本局和累计。
- [ ] AC7：普通碰及全部杠类型都不修改个人倍率；连续放赖按 1→2→4 翻倍，新一局重置为 1。
- [ ] AC8：明杠/特殊碰杠 3×、暗杠每家 2×、补杠每家 1×均有零和回归测试，且不乘个人倍率。
- [ ] AC9：先杠后胡与先杠后流局的本局净变化均正确，流局保留杠分。
- [ ] AC10：SQLite 运行和部署保持不变，PostgreSQL 仅作为后续账号功能前置迁移建议记录。
- [ ] AC11：定向测试、全量 lint、type-check、tests、build 与 Compose 配置检查全部通过。

## Out of Scope

- 本轮不实现 PostgreSQL、双库适配、注册登录、跨设备账号恢复、名称修改 API 或头像上传。
- 不实现读取对手暗牌或牌墙顺序的作弊机器人。
- 不引入点炮、防守危险牌、吃牌、特殊番型或新的计分规则。
- 不修改现有协议中的结算字段，仅精简本轮 UI 消费。
