# 四位房间码、机器人难度与赖子软胡修复

## Goal

降低好友房邀请码的输入成本，让房主可按需要补充机器人并控制机器人胡牌能力，同时确保牌桌布局和“两个天然对子加一张赖子”组成标准 `3n+2` 软胡的规则在全链路稳定生效。

## Background

- 当前产品同时支持好友房和一人三机器人模式。
- Web 与微信小程序共享协议、服务端和规则引擎，但入口表单、房间控制器与等待页是两套独立实现；本任务要求两端同步交付，不允许只更新其中一端。
- 用户希望好友房代码缩短为四位数字。
- 新房号确定为 `1000–9999`，不生成前导零；旧六位活动房间需要平滑兼容。
- 好友房创建后，房主需要能够向空座添加机器人，并为机器人选择两级难度。
- 人机对战创建时也需要选择相同的机器人难度。
- 难度语义已确认：低难度机器人只允许硬胡；高难度机器人允许硬胡和软胡。
- 机器人难度是房间级统一配置；好友房内所有机器人共用一个难度，人机房的三名机器人也共用该配置。
- 新旧房间和未显式传难度的旧客户端默认使用高难度，以保持当前机器人可硬胡、可软胡的行为。
- 历史决策要求真人满足软胡时，倒计时结束后的托管可以自动胡；机器人难度不得改变真人或托管控制器的该行为。
- 胡牌规则仍以四组面子加一对将（`3n+2`）为基础；赖子参与构型时应归类为软胡。

## Requirements

### R1 四位数字房间码

- 新创建的房间生成 `1000–9999` 范围内的四位纯数字房间码。
- 房间码必须在当前活跃房间中唯一。
- 加入、恢复、分享和房间展示等既有入口以四位码为主，并继续接受仍存活的六位旧房号。
- 已持久化的旧格式房间在升级后不能导致服务启动失败。
- Web 邀请链接、小程序分享参数、手动加入表单、聊天和房间恢复统一支持新房号契约。

### R2 好友房房主添加机器人

- 好友房创建后、牌局开始前，房主可以向空座添加机器人。
- 非房主不能添加机器人。
- 等待阶段有真人加入而四席已含机器人时，自动移除一名机器人并让真人入座；真人优先于机器人。
- 房主可在开局前手动移除机器人，重新腾出空座。
- 添加的机器人参与准备和开局流程，不要求真实玩家占满四席。
- 机器人加入后需要明确归属于当前房间，并在离房、解散、恢复和下一局流程中保持一致。

### R3 进行中加入与每局重新准备

- 好友房牌局进行中仍允许新真人加入房间，但新加入者先以观战/候补身份进入，不影响当前四席牌局。
- 观战者可读取公开牌局信息，不得读取任何玩家暗手牌或提交牌局动作。
- 观战只用于替补当前局中的机器人：房间内真人总数最多四名；牌桌已是四名真人时拒绝新的加入请求。
- 当前局结算结束后，按观战真人的加入顺序替换机器人并进入等待牌桌。
- 每一局开始前所有本局真人座位都必须重新准备；机器人视为自动准备。

### R4 两级机器人难度

- 好友房由房主设置统一机器人难度，随后添加的所有机器人都使用该难度。
- 人机对战创建时可选择相同的难度。
- 机器人难度进入共享协议、服务端房间状态、持久化快照和客户端房间投影。
- 低难度机器人只在满足硬胡时执行自摸。
- 高难度机器人在满足硬胡或软胡时都可以执行自摸。
- 难度只改变机器人是否执行胡牌，不改变真人玩家规则、牌墙、摸打牌合法性或结算倍率。
- 低难度限制只作用于 `BOT` 控制器；真人断线后的 `TRUSTEE` 继续按真人合法动作自动胡牌。
- Web 与小程序均提供创建时难度选择、好友等待房难度设置和当前难度展示。

### R5 双将摸赖子的软胡判定

- 当手牌中存在两个天然对子，且此前没有赖子时，摸入一张赖子后，可用赖子把其中一个对子补成刻子、另一个对子作为将，从而构成完整 `3n+2` 牌型并判定可胡。
- 该胡牌必须归类为软胡，不能归类为硬胡。
- 此时真人玩家可以直接选择软胡，也可以选择放赖并补摸一张牌继续追求硬胡。
- 如果最后摸到的是两个天然对子中任意一种相同牌，使其中一对直接成为刻子，则判定为硬胡。
- 判定需覆盖服务端合法动作、结算、听牌提示和机器人决策所复用的统一规则路径。
- 既有“多赖子禁胡”“赖子与任意摸牌成将禁胡”等项目特殊限制不得被意外放宽。

### R6 上家公开牌避让弃牌区

- 上方玩家碰、杠、放赖较多时，不得与上方弃牌展示重叠。
- 上方玩家的公开牌组改为在头像左侧可用区域内展开，并保持与该玩家身份的视觉归属。
- 稀疏、满组、长昵称和小屏横屏状态下均不得遮挡头像、中央牌桌、牌河或其他玩家区域。
- Web 与小程序的相同座位语义保持一致。

### R7 小程序沉浸式横屏

- 微信小程序横屏牌桌应尽可能移除顶部“晃晃牌桌”白色系统长条，使用完整可用屏幕展示游戏。
- 必须基于微信小程序正式支持的窗口配置实现，不依赖仅开发工具可用或审核不兼容的技巧。
- 刘海、安全区、胶囊按钮和返回/离房能力必须保留，不得因沉浸式展示导致关键操作不可达。
- Web/PWA 的窗口和导航行为不因该调整回退。

## Acceptance Criteria

- [x] 新房间生成无前导零的四位纯数字码，并发或碰撞时不会覆盖活跃房间。
- [x] 旧格式持久化房间可安全恢复或按既有生命周期清理。
- [x] 好友房房主可在开局前添加机器人直至四席，非房主请求被服务端拒绝。
- [x] 等待阶段真人加入满含机器人的四席时会替换机器人；房主也可手动移除机器人。
- [x] 牌局进行中加入的真人只能观战公开信息，不能看到暗牌或执行牌局动作。
- [x] 结算后房间回到等待阶段，候补真人按顺序进入下一局座位，所有真人必须重新准备，机器人自动准备。
- [x] 好友房内所有机器人和人机房三名机器人均使用房间级所选难度，客户端可读取并展示该配置。
- [x] 低难度机器人不会选择软胡；高难度机器人可以选择硬胡和软胡。
- [x] “两个天然对子 + 摸入一张赖子”能够按完整手牌结构判为软胡，并产生正确倍率。
- [x] 上述软胡状态同时保留“自摸”和“放赖”合法动作；放赖补摸后按新牌重新判定。
- [x] 直接摸到两个天然对子中的任意一种相同牌时判为硬胡。
- [x] 该牌型对应的听牌辅助会包含赖子（手中已有赖子时继续遵守现有排除规则）及真实公开剩余数。
- [x] 共享协议、游戏引擎、房间服务和小程序均有针对性测试。
- [x] Web 与小程序的创建、加入、好友等待房机器人管理和观战状态行为一致。
- [ ] 上方玩家四组碰杠并带放赖时，公开牌位于头像左侧且不与上方弃牌区重叠。
- [ ] 小程序真机横屏使用支持的沉浸式窗口配置，顶部白色导航条消失，安全区与离房操作仍可用。
- [x] 全量 lint、类型检查、测试、Web 构建和小程序生产构建通过。

## Out of Scope

- 不新增第三级机器人难度或通用 AI 策略系统。
- 不调整真人玩家的胡牌限制和倍率定义。
- 不改变碰、杠、放赖、响应倒计时或出牌时长设置。
- 本次不实现任何语音消息、实时语音、语音转文字、录音回放或视频通话能力。
