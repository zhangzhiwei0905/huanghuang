# 机器人转真人积分重算与来由玩法

## 背景

当前房间支持两种模式：`FRIEND`（等 4 个真人）和 `BOT`（真人 + 机器人）。玩家创建房间后，希望能先带机器人开局练手，等好友陆续进来后再打正式局。此外，晃晃规则中还缺少「来由」这一玩法分类和对应的倍率、音效。

本任务是父任务，持有完整的原始需求集合、子任务地图和跨子任务验收标准，本身不作为实现目标。

## 原始需求

1. 创建玩家房间后，可以先加入机器人玩，但是一旦 4 个玩家准备好之后，积分要重新计算。
2. 增加「来由」的玩法：
   - 核心：放赖子之后会摸一张牌，如果此时能构成胡牌，那么就叫来由。
   - 分类：
     - 硬来由：手上只有一张赖子，放赖后摸了一张牌能构成硬胡。
     - 软来由：手上可能有 1 张或多张赖子，放赖后摸了一张牌能构成软胡（此时手牌里有且只有一张赖子）。
     - 边界确认：手上原有 2 张赖子、放掉 1 张后摸牌构成硬胡（剩下那张赖子作为它本身的牌面参与构型，没有替代别的牌），也是硬来由。
   - 奖励：如果玩家最终是来由，倍率再 ×2。
   - 音效：来由分硬来由和软来由，暂时分别复用硬胡、软胡音效，后续会替换为专门音效，需要预留设计。

## 已确认的需求决策

| 议题 | 决策 |
|---|---|
| 需求 1 中「积分重新计算」的语义 | 清零重新开始计分，且是**房间级一次性**行为。本房间首次以 4 个真人满座开局时，所有座位的累计积分归零；此后玩家掉线被机器人顶替、再重连入座导致重新满座，都不再清零，掉线前的积分继续有效。想要全新账本只能重新创建房间。 |
| 来由 ×2 与放赖倍率的关系 | 叠加。最终倍率 = 胡型基础倍率 × 2^放赖次数 × 2（来由）。理论最高倍率由 32 倍提升到 64 倍。 |
| 音效落地方式 | 来由音效走独立的语义事件通道，当前映射到 `yinghu.mp3` / `ruanhu.mp3`，后续只需替换文件映射即可。 |

## 跨子任务验收标准

1. `pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm build` 全部通过。
2. 结算零和不变量在两个改动后依然成立（`assertZeroSum` 不抛错）。
3. 客户端不自行判定胡型、来由或倍率，全部由服务端投影下发。
4. 现有房间快照（不含新字段的历史数据）可以正常反序列化，新字段有兼容默认值。
5. Web 与小程序两端结算展示保持一致的语义，小程序音效不出现重复播放或漏播。

- 不引入新的房间模式或重构 `FRIEND` / `BOT` 模式语义。

## 需求变更记录

规划期的两条决策在实现后被用户修正：

1. **积分清零**由「含机器人的历史局分不计入战绩」改为**房间级一次性**：本房间首次四真人满座开局时清零一次，之后玩家掉线被机器人顶替、重连回座位都不再清零，换账本只能重建房间。实现从 `scoresIncludeBotRounds`（每局重新武装）改为 `fullTableScoreResetDone`（单向翻转），见提交 `fa8b4a9`。
2. **硬来由边界**确认：手上原有 2 张赖子、放掉 1 张后摸牌构成硬胡（剩下那张赖子作为自身牌面参与构型），算硬来由。原实现按引擎 `winType` 判定，本身已正确，补测试固定，见提交 `730c355`。

### 部署过程中发现的基础设施问题（未根治）

1. `README.md` 的阿里云部署章节与生产实际不符：文档写 `docker compose up -d --build` + caddy 容器 + `deploy_game_data` 卷，生产实际是 `docker run` + 宿主机 nginx（`/etc/nginx/conf.d/huanghuang.conf` → `127.0.0.1:13000`）+ `huanghuang_game_data` 卷。照文档执行会起出平行 stack 并抢占 80/443。
2. Docker 专属加速器 `eznmnf0f.mirror.aliyuncs.com` 对 `node:24-alpine` 返回 403，构建直接失败。本次绕过方式：先 `docker pull node:24-alpine` 让 daemon 回退到备用源 `docker.m.daocloud.io`，再用 `docker build --pull=false`。根治需要改 `/etc/docker/daemon.json` 并重启 Docker，会连带重启同机的其他项目容器，需要维护窗口。
3. 生产服务器没有 `rsync`，且 `~/huanghuang` 不是 git 仓库。本次用 `git archive HEAD | ssh … tar -x` 推送提交树，注意这种方式不会删除服务器上已从 git 移除的旧文件。
