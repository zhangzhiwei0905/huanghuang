# 四位房间码、机器人难度与赖子软胡修复：技术设计

## 1. 设计目标

在不拆分现有单机 `RoomService + SQLite JSON snapshot` 架构的前提下完成以下关联改造：

1. 新好友房生成易输入的四位房号，并兼容仍存活的六位旧房间。
2. 好友房可混合真人和机器人，进行中加入的真人只替补机器人；Web 与小程序行为一致。
3. 机器人难度只约束机器人是否接受软胡，真人规则、托管规则和结算保持不变。
4. 用跨层回归测试固定“双对子摸赖子”的软胡、放赖与硬胡分支。
5. 调整上方玩家公开牌布局，并让小程序牌桌使用正式支持的沉浸式横屏窗口。

## 2. 已确认边界

- 新房号范围为 `1000–9999`，不生成前导零。
- 真人总数最多四名。观战者只用于替补当前牌局中的机器人，不实现五人以上轮换。
- 等待阶段真人优先于机器人；进行中加入者在本局结束后按加入顺序替换机器人。
- 等待阶段仍只有四个固定座位，不同时保留第二套候补结构。
- 所有人类座位每局都必须重新准备；机器人自动准备。
- 房间统一机器人难度：`LOW` 只接受硬胡，`HIGH` 接受硬胡和软胡，默认 `HIGH`。
- 难度限制仅作用于 `BOT`；真人断线后的 `TRUSTEE` 继续按全部真人合法动作自动行动。
- Web 和微信小程序必须同步更新。

## 3. 共享协议

### 3.1 房号

协议提供唯一的 `roomCodeSchema`，加入房间和聊天共同复用：

```ts
const roomCodeSchema = z.string().regex(/^(?:[1-9]\d{3}|\d{6})$/u);
```

- 服务端只生成四位新码。
- 六位只作为旧活动房间、旧邀请链接和旧本地恢复状态的迁移兼容。
- Web 与小程序表单主要文案展示“四位房号”，但校验层仍可接受六位旧码。

### 3.2 机器人难度与房间命令

```ts
type BotDifficulty = "LOW" | "HIGH";
```

- `createRoomSchema` 增加 `botDifficulty`，默认 `HIGH`。
- 房间设置接口允许房主在 `FRIEND + WAITING` 修改 `botDifficulty`。
- 增加好友房添加机器人、移除指定机器人所需的请求 schema。

### 3.3 投影

`RoomProjection` 增加：

- `botDifficulty`
- `selfRole: "PLAYER" | "SPECTATOR"`
- `spectators: { nickname, isSelf, connected }[]`

`LobbySeatProjection` 增加 `controller: "HUMAN" | "BOT" | null`。机器人座位：

- `occupied = true`
- `ready = true`
- `connected = true`
- 不拥有 `sessionId`，也不能成为房主或自己

## 4. 服务端房间模型与生命周期

### 4.1 状态

`RoomState` 增加：

```ts
botDifficulty: BotDifficulty;
spectators: {
  sessionId: string;
  nickname: string;
  avatarUrl: string | null;
  connected: boolean;
  joinedAt: string;
}[];
```

旧快照缺字段时分别回退为 `HIGH` 和空数组。SQLite 表不迁移，继续保存 JSON。

### 4.2 四位码分配

- 从 9000 个候选中随机选一个起点。
- 从该起点环形扫描整个 `1000–9999` 空间，返回第一个不在 `roomsByCode` 的房号。
- 只有 9000 个活动四位码全部占用时才失败，避免固定 100 次随机重试在碰撞时误报。
- 六位旧码可与四位新码同时存在。

### 4.3 添加与移除机器人

- 仅房主、仅 `FRIEND + WAITING` 可操作。
- “添加机器人”填充第一个 `EMPTY` 座位。
- “移除机器人”必须指定当前为 `BOT` 的座位。
- 修改座位或难度后清空真人准备状态，避免在房间条件变化时沿用旧确认。
- 添加最后一个机器人后不直接强制开局；统一通过“所有真人已准备且四席非空”的开局条件判断。机器人视为自动准备。

### 4.4 真人加入

`joinRoom` 使用以下顺序：

#### `WAITING`

1. 已是座位成员则幂等返回。
2. 有 `EMPTY` 座位时进入第一个空座。
3. 无空座但有 `BOT` 时替换第一个机器人并成为未准备真人。
4. 四席均为真人时返回 `ROOM_FULL`。

#### `PLAYING` / `ROUND_RESULT`

1. 仅 `FRIEND` 可加入；`BOT` 模式仍不可邀请。
2. 统计座位真人与观战真人；达到四人返回 `ROOM_FULL`。
3. 只有当前局存在可被替换的机器人座位时才加入 `spectators`。
4. 观战者成为房间成员，可订阅投影和主动离房，但 `selfSeat = null`、无暗牌、无合法动作。

### 4.5 局末回到等待房

好友房 `ROUND_RESULT → WAITING` 时：

1. 同步本局积分和下一庄。
2. 按 `joinedAt` 顺序将观战真人放入机器人座位。
3. 清空观战队列。
4. 保留四个固定座位，清空全部真人准备状态。
5. 重新开始等待房超时计时。

若进行中真人主动离房，其座位继续由机器人完成当前局；局末该机器人座位同样优先接纳观战真人。座位累计积分沿用现有按座位保存的语义。

### 4.6 成员、房主与连接

- `hasMember` 同时识别座位真人和观战真人，保证 Socket 订阅与刷新恢复。
- 观战者不得执行游戏命令、准备、设置、添加/移除机器人或发送依赖座位展示的牌桌聊天。
- 观战者离房只从队列移除。
- 房主离房时优先转让给仍在房间的其他真人，包括观战者；无人时关闭房间。
- `setConnected` 同时更新座位真人与观战真人的连接状态。

## 5. 机器人难度

### 5.1 决策边界

规则引擎仍负责计算 `DECLARE_WIN` 是否为合法动作以及本次是 `HARD` 还是 `SOFT`。机器人策略获得当前 `winType` 和房间 `botDifficulty`：

- `HIGH + HARD/SOFT`：声明胡牌。
- `LOW + HARD`：声明胡牌。
- `LOW + SOFT`：不声明胡牌，继续执行已有放赖、杠或弃牌策略。

不从规则引擎删除 `DECLARE_WIN`，否则会把房间配置误写进真人规则。真人超时仍由 `trusteeAction` 接受合法胡牌。

### 5.2 持久化和修改

- 人机房在创建时设置难度，续局保持不变。
- 好友房创建时可给初始值，等待页房主可修改。
- 旧请求和旧快照默认 `HIGH`，保持当前机器人行为。

## 6. 双对子赖子牌型

代码研究表明，当前 `evaluateWin` 的通用替换分支已经能够把摸入的唯一赖子替换成某个对子牌，形成“一刻子 + 另一对子”的软胡分解。因此本任务采用“先复现跨层、只在失败层修复”的方式：

1. 引擎测试：`三组面子 + 两个天然对子 + 摸入唯一赖子` 为 `SOFT`。
2. 回合测试：同一状态同时提供 `DECLARE_WIN`、`CONTINUE_TURN` 和 `RELEASE_WILDCARD`。
3. 硬胡对照：摸到两个对子中的任意同种牌为 `HARD`。
4. 听牌测试：弃牌后等待赖子时显示软胡；等待对子同种牌时显示硬胡。
5. 服务投影测试：合法动作、合并倍率和公开剩余数正确。

若这些测试已全部通过，不对分解器做无依据重写；若某一层失败，只修复该层并保留现有多赖子与任意牌成将禁胡测试。

## 7. Web 与小程序

### 7.1 创建/加入

两端创建好友房和人机房都展示统一的低/高难度选择，默认高难度。加入表单：

- 主提示为“四位房号”
- 手动输入以四位为主，但输入框最多保留六位以兼容旧活动房间
- 从旧邀请或恢复状态进入时仍接受六位旧码

### 7.2 好友等待房

房主看到：

- 当前统一机器人难度选择
- “添加机器人”按钮，逐次填充空座
- 每个机器人座位上的“移除”动作

所有玩家都能看到机器人身份、难度、自动准备状态。真人加入替换机器人后，该座位立即显示真人未准备。

### 7.3 观战

- Web 与小程序在 `selfRole === "SPECTATOR"` 时仍渲染公开牌桌。
- 统一显示“观战中，本局结束后自动入座”提示。
- 所有玩家可看到候补人数或昵称，但观战者没有手牌、动作栏或聊天输入。
- 观战者使用固定的桌面视角；局末投影变为 `PLAYER + WAITING` 后自然进入准备页。

### 7.4 上方玩家公开牌布局

- 小程序将 `player-meld-rail.pos-opposite` 从牌桌上方中轴线移到上方玩家头像左侧。
- 公开牌组继续保持横向阅读，并设置由安全区、头像宽度和左侧边界共同约束的最大宽度；牌组较多时向左侧扩展和紧凑换行，不侵入上方弃牌区。
- 碰、杠、放赖继续使用统一公开牌组件，只改变上方座位的容器定位，避免产生不同规则展示。
- Web 同步检查顶部座位四组公开牌的极限状态；如现有站内换行仍可能进入弃牌区，则采用同一“头像左侧独立轨道”语义。
- 验证四组杠牌、混合碰杠放赖、长昵称、最小支持横屏尺寸和刘海屏安全区。

### 7.5 小程序沉浸式横屏

- 仅房间牌桌页设置 `navigationStyle: "custom"`，移除原生标题导航条；`pageOrientation: "landscape"` 和 `disableScroll` 保持不变。
- 微信右上角胶囊仍由系统显示，牌桌使用窗口安全区和胶囊位置信息预留右上角交互空间。
- 现有离房/返回按钮承担自定义导航职责，并覆盖正常返回、房间内确认离开和页面卸载清理。
- 首页、登录页等非牌桌页面继续使用原生导航，不扩大改动范围。
- 开发者工具只用于构建和基本布局检查；最终兼容性以至少一台刘海屏真机和一台普通横屏真机为准。

## 8. 兼容、风险与回滚

- 旧六位房间：不改码，继续可恢复和加入；新房只生成四位。
- 旧客户端：创建时缺难度按 `HIGH`；服务端仍是权限和成员状态权威。
- 旧快照：缺难度和观战队列安全归一化。
- 旧版本回滚不能理解新观战队列，生产部署前必须备份 SQLite 和旧镜像。
- 最大风险是再次出现“座位成员 + 等待成员”双重来源。本设计规定观战队列只存在于 `PLAYING/ROUND_RESULT`，进入 `WAITING` 前必须全部消费或清空。
- 第二风险是观战者泄露暗牌。投影继续只对 `selfSeat` 返回手牌，`selfSeat = null` 时四家手牌全部为 `null`。
- 第三风险是 Web、小程序入口校验不一致。共享正则契约配合两端组件/API 测试与生产构建共同验证。
- 第四风险是自定义导航后内容进入胶囊或刘海安全区。房间页必须基于运行时窗口信息计算安全内边距，并保留离房入口。
