# 修复排位页面重复打开与实时连接重连

## Goal

消除手机端排位牌局中反复从右侧滑入新牌桌页面、随后出现
`websocket error` 并持续重连的问题，让单次匹配只打开一个牌桌页面，
并让瞬时断线能够稳定恢复到同一牌局。

## Background

- 大厅页在匹配状态为 `MATCHED` 时会调用
  `Taro.navigateTo({ url: "/pages/room/index" })`。
- 大厅页进入牌桌后仍保留在页面栈中，其匹配轮询 effect 继续运行；当前
  `matchedRoomOpeningRef` 只覆盖一次 `navigateTo` Promise，导航完成后会重置，
  因此后续相同 `MATCHED` 响应可以再次压入牌桌页。
- 每个牌桌页都会调用 `useRoom()` 并创建自己的 Socket。重复页面会造成多条
  实时连接和页面滑入动画。
- `useRoom` 同时启用了 Socket.IO 内建自动重连和 `connect_error` 后 2 秒
  强制递增 `socketGeneration` 的重建机制；内建重连即使成功，遗留的强制
  重建定时器也不会在成功订阅后取消。
- 连接状态不是 `connected` 时，牌局操作按现有安全规则保持锁定，避免离线
  操作基于过期投影提交。

## Requirements

- R1：大厅页隐藏后不得继续因为轮询到同一个 `MATCHED` 状态而自动打开新的
  牌桌页。
- R2：大厅页重新显示时仍须重新读取服务端匹配状态；如果玩家仍在有效牌局中，
  应允许恢复进入该牌局。
- R3：同一可见大厅生命周期内，同一个匹配结果只能触发一次自动开桌；新的
  `matchId` 仍可正常打开。
- R4：牌桌实时连接使用单一、可预测的重连所有权。瞬时 transport error
  交给 Socket.IO 内建退避处理，不得同时无条件销毁正在恢复的 Socket。
- R5：Socket 每次重新连接后必须重新订阅房间，并且只有在收到新房间投影后
  才恢复 `connected` 状态和牌局操作。
- R6：服务器主动断开且不会自动恢复的场景仍须具备有界的硬重建兜底。
- R7：保留现有连接中断时锁定操作、重连后不回放历史音效的行为。
- R8：补充自动化测试，覆盖页面可见性/同匹配去重和重连策略的关键分支。

## Acceptance Criteria

- [x] AC1：手机端单次排位匹配只出现一次从大厅到牌桌的右滑导航，持续游戏
  期间页面栈不再被同一匹配结果重复压入。
- [x] AC2：从牌桌主动返回大厅或小程序从后台恢复后，服务端状态仍为有效
  `MATCHED` 时可以按现有产品规则恢复牌局。
- [x] AC3：瞬时 `connect_error` 不会在内建重连成功后再由遗留的 2 秒定时器
  销毁新连接。
- [x] AC4：`io server disconnect` 或内建重连耗尽时仍会执行一次有界硬重建，
  不会形成无上限的高频重建循环。
- [x] AC5：重新连接后，在房间订阅投影返回前，所有游戏操作仍保持不可用；
  投影成功应用后恢复操作。
- [x] AC6：相关单元测试、mini-program typecheck/build 和仓库既有测试通过。

## Out of Scope

- 不修改服务端匹配规则、牌局托管规则或协议结构。
- 不改变小程序页面转场样式。
- 不在本任务中调整音频播放器；重连后历史音效静默只作为回归约束。
