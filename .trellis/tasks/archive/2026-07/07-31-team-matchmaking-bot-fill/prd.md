# 匹配算法简化（单排/组队排位统一，不再考虑段位）

## Goal

当前匹配算法是"入队时间锚点 + 动态段位容差（10/20/40秒阶梯放宽）+ 最近对手规避排序"的贪心算法，规则复杂、临界值处体验会突变，且段位容差在稀疏在线场景下可能长时间凑不齐人。产品决定简化：**单人排位和组队排位统一使用同一套不考虑段位的匹配逻辑**——组队排位里只有1人排队时，效果就等价于单人排位，不再是两套规则。人数不足4人时，先短暂尝试匹配其他真实玩家/队伍凑桌（不看段位），短暂等待后仍不足，直接从预置机器人池随机抽取机器人补满4人开局。

## Requirements

- 匹配真人时不再做任何段位/大段位兼容性限制——只要不拆散已有 party，任意段位组合都视为兼容，删除 `matchmakingMajorTierRange` 那套按等待时间阶梯放宽的逻辑（连同 `majorTierDistance` 一起视为死代码删除）。
- 候选组排序不再考虑段位差异（删除 `groupSpread`/`totalPairDistance` 相关比较），只保留"最近对手规避"和"先入先出"作为排序依据。
- 短暂等待（沿用现有 `MATCHMAKING_BOT_FILL_WAIT_MS`，约5秒）后仍未凑满4名真实玩家，则从预置机器人池中**完全随机**抽取机器人补满剩余座位，不做段位兼容性过滤、不做"最近未使用优先"的轮换/去重控制（每次都是纯随机，允许连续抽到同一批机器人）。
- **不拆分单排/组队两条撮合管线**——两者继续共用同一套候选池、同一套算法，只是入口（单排 `enqueue()` / 组队 `enqueueParty()`）不同。这样"组队排位只有1人"天然等价于单排。
- `allowBots`（是否允许机器人补位）这个用户偏好开关维持现状不变，本次只改"匹配时看不看段位"和"机器人怎么选"，不改"要不要给机器人补位"这件事本身的开关机制。
- Party 完整性约束（同一队伍不能被拆散到不同桌）、正好4人时直接开局不等待，均保持不变。
- 不改变游戏对局本身的规则（4人开局后的游戏玩法不受影响），只改匹配撮合逻辑。

## Acceptance Criteria

- [x] 队伍/单人人数凑够4人时，发起匹配后立即开局，不受影响。
- [x] 人数不足4人时，短暂等待窗口内如果有其他真实玩家/队伍可以凑够4人（不论段位差多大），能够正常撮合开局。
- [x] 短暂等待窗口结束后仍不足4人，自动从机器人池随机抽取机器人补满4人并开局，不因段位不兼容而拒绝或继续等待。
- [x] 组队排位里只有1人排队时，撮合结果与该玩家直接走单人排位入口排队一致（同一套规则）。
- [x] 服务端单测/集成测试覆盖：真人凑桌成功（含段位差很大的组合）、真人凑桌超时转机器人随机补位、party 不被拆散 三种场景；原有"按段位限制/排序"的旧测试用例按新行为更新或移除。
- [x] TypeScript 编译通过，无新增 lint 错误。

## Notes

- 现状算法排查见对话记录：核心逻辑在 `apps/server/src/matchmaking-algorithm.ts`（`selectMatchmakingGroup`/`mutuallyCompatible`/`matchmakingMajorTierRange`/`selectBotFillGroup`）与 `apps/server/src/matchmaking-service.ts`（`tick`/`MATCHMAKING_BOT_FILL_WAIT_MS`）。
- 用户明确决策：① 不拆分单排/组队管线，统一成一套算法；② 保留"先短暂尝试匹配真人，超时后机器人补位"的两段式流程；③ 机器人抽取完全随机，不做去重/轮换控制；④ 这是全局改动，单人排位的匹配范围也会一并放开，不再按段位限制。
