# 技术设计：单人/组队排位、统一段位展示与晋升反馈

## 1. 范围与边界

本任务覆盖 `packages/protocol`、`apps/server`、`apps/miniprogram`，不改变麻将规则与现有段位结算算法。

- `protocol` 定义新的房间模式、组队匹配投影和请求契约。
- `server` 负责组队房间、整队入队/取消、不可拆分分组、竞技房创建及持久化。
- `miniprogram` 负责双排位入口、组队等待牌桌、统一玩家详情、段位徽章和晋升动画。
- 段位徽章作为小程序源代码资产提交，不依赖 Figma 运行时或远程图片。

## 2. 协议设计

### 2.1 房间模式

`RoomMode` 新增 `TEAM_MATCH`：

- `FRIEND`：现有好友房，四座占满且真人全准备后自动开局。
- `BOT`：现有人机房。
- `TEAM_MATCH`：组队排位等待房，只负责组队与排队，不自动开局。
- `MATCH`：匹配完成后创建的正式竞技对局，保持现有单局结算语义。

`TEAM_MATCH` 可由客户端创建，但服务端固定底分、出牌时长和机器人难度，并禁止设置与机器人管理接口。

### 2.2 组队匹配投影

`RoomProjection` 新增 `teamMatchmaking`：

```ts
type TeamMatchmakingProjection =
  | { status: "IDLE" }
  | { status: "QUEUED"; enqueuedAt: string; memberCount: number }
  | { status: "MATCHED"; matchId: string; roomId: string };
```

非 `TEAM_MATCH` 房间始终为 `null`。该状态由服务端数据库中的队伍排队条目与当前竞技对局推导，客户端不自行推算。

`MatchmakingState.QUEUED` 增加可选 `partyRoomId`，用于从主页/前后台恢复到组队牌桌。单排条目没有该字段。

### 2.3 操作接口

- `POST /api/rooms`：允许创建 `TEAM_MATCH`。
- `POST /api/rooms/:code/ready`：`TEAM_MATCH` 只修改准备状态，不自动开局。
- `POST /api/rooms/:code/team-matchmaking`：房主发起整队匹配。
- `DELETE /api/rooms/:code/team-matchmaking`：任一当前队员取消整队匹配。
- 既有 `DELETE /api/matchmaking/queue` 若发现调用者属于队伍，也取消整队，保证主页恢复路径一致。

开始匹配的服务端校验：

1. 房间必须为活动中的 `TEAM_MATCH/WAITING`。
2. 调用者必须是房主。
3. 当前必须有 2–4 名真人玩家，无机器人或观战者。
4. 所有当前玩家均已准备并已绑定微信竞技身份。
5. 所有玩家均无活动竞技对局或其他排队条目。

取消匹配会原子删除队伍全部排队条目，然后清空房间全部准备状态。

## 3. 数据与匹配算法

### 3.1 数据库迁移

`matchmaking_entries` 增加两个可空字段：

- `party_id TEXT`：`TEAM_MATCH` 房间 ID；单排为 `NULL`。
- `party_size INTEGER`：入队时冻结的队伍人数；单排为 `NULL`。

新增 `party_id` 索引。现有记录通过可空列保持兼容。

新增数据库方法：

- 批量、事务化插入一个队伍的全部排队条目。
- 按 `party_id` 查询与删除全部排队条目。
- 查询成员所在的队伍条目。

连接/心跳仍以玩家为单位更新，但调度时只允许一个队伍在所有冻结成员均在线时进入候选集；任一成员超出断线宽限后，整队排队取消并由房间投影回到 `IDLE`。

### 3.2 不可拆分匹配

匹配候选仍是四名玩家，但每个候选带 `partyId/partySize`：

- 生成四人组合后，校验组合中每个 `partyId` 的出现次数等于其冻结 `partySize`。
- 同一队伍成员之间不应用段位距离过滤；队伍与外部玩家之间仍应用现有等待时间扩圈规则。
- 排序继续优先等待时间、较小段位跨度和较少近期重复对手。
- 单排玩家视为大小为 1 的独立分组。

因此合法组合包括 `1+1+1+1`、`2+1+1`、`2+2`、`3+1`、`4`，不会把队伍拆到不同牌桌。

匹配成功后继续调用现有 `RoomService.createCompetitiveMatch`，生成新的 `MATCH` 房间并复用现有竞技结算事务。队伍等待房保留短期恢复状态；成员客户端拿到 `MATCHED` 后切换到正式房间。

## 4. 房间生命周期

- 创建：房主进入 `TEAM_MATCH/WAITING`，四个座位中仅房主占用。
- 加入：仅在队伍未排队时允许通过房间号加入。
- 准备：2–4 名玩家各自准备，不自动开始。
- 开始匹配：房主触发，冻结当前成员集合并整队入队。
- 排队中：禁止加入、切换准备、修改规则；所有成员可取消。
- 取消/离队：先取消整队，再清空全员准备；离队后按现有规则转移房主或关闭空房。
- 匹配成功：客户端通过房间投影或竞技状态得到新 `MATCH` 房间并切换。
- 解散：房主解散前先取消整队排队，避免残留条目。

## 5. 小程序交互

### 5.1 主页

- 账号头像整体成为可点击目标，打开 `PlayerProfileModal`。
- 排位入口改为两个主按钮/卡片：
  - 单人排位：复用现有 `competitiveApi.queue`。
  - 组队排位：创建 `TEAM_MATCH` 房并进入房间页。
- 若恢复状态是组队排队，主页直接恢复对应队伍牌桌；若已匹配则进入正式竞技房。

### 5.2 组队牌桌

复用现有等待房四方座位布局，但按模式替换中央信息与操作：

- 标题为“组队排位”，显示房号、当前人数和准备数。
- 隐藏底分、难度、添加机器人。
- 未匹配时每个玩家可准备/取消准备。
- 房主在 2–4 人全准备后可“开始匹配”。
- 匹配中所有成员看到等待时长并可“取消匹配”。
- 非房主看到“等待房主开始匹配”。

### 5.3 统一段位组件

新增 `RankBadge`：

- 输入 `CompetitiveRankDisplay`、尺寸和可选紧凑样式。
- `majorIndex` 映射 8 个 SVG 徽章。
- 图标下统一显示 `displayName`。

用于主页账号区、玩家详情、排队状态、结算段位区和晋升动画。布局紧凑处可以缩小图标，但不省略段位文字。

### 5.4 晋升动画

新增 `RankPromotionOverlay`：

- 触发条件封装为纯函数，只有 `afterRankLevel > beforeRankLevel` 且段位文字变化时返回 true。
- 首次拿到该结算 `matchId + afterRankLevel` 时显示，组件卸载或同一键重复投影不重播。
- 动画序列：旧徽章淡出/后退 → 光带扫过 → 新徽章弹入 → 文案落位。
- 约 2.2 秒后自动收起，结算弹窗继续可操作。
- `prefers-reduced-motion` 下取消缩放与位移，仅保留短淡入淡出。

## 6. 兼容与失败处理

- 新列均为可空，旧数据库启动时使用幂等 `ALTER TABLE`。
- 旧的 `FRIEND/BOT/MATCH` 投影行为不改变。
- 小程序的投影兼容层为旧服务端补 `teamMatchmaking: null`。
- 队伍批量入队和比赛创建使用数据库事务及队列版本校验。
- 匹配创建冲突不消费任何队员条目，下一个调度周期重试。
- 队伍成员身份失效、断线超时或队伍记录不完整时取消整队，而不是降级拆队。

## 7. 回滚

- UI 可先隐藏“组队排位”入口，不影响单排与已有房间。
- `party_id/party_size` 为附加可空列，代码回滚后旧版本会忽略，不需要破坏性迁移。
- 徽章与动画均为展示层，可独立回退到纯文字段位。
