# 好友组队与机器人排位体验升级

## Goal

在体验阶段保证排位可以稳定开局，并把单人排位、好友组队、房间等待、机器人补位整合为一条清晰流程；同时提供完整的好友添加、确认、在线状态和邀请入房能力。

## Background

- 当前人数不足时，组队排位可能无法开局。
- 体验版已有 10 个预置机器人，但实际匹配经常只出现“赌侠”“赌圣”“赌王”。
- 当前主页按钮过大且操作入口堆叠，单人排位与组队排位被割裂。
- 当前缺少可通过对局头像或玩家 ID 建立关系的好友系统。
- 仓库包含 Web 和微信小程序两个客户端；当前开发分支为 `miniprogram`，近期排位与玩家详情体验主要在小程序端交付。
- 现有组队排位房已支持 2-4 名真人整队入队，但 `enqueueParty()` 会把 `allowBots` 固定为 `false`，因此组队队列不能走机器人补位路径（`apps/server/src/matchmaking-service.ts`）。
- 现有机器人补位直接从空闲机器人数组头部 `slice()`，没有按真人段位筛选或轮换；机器人数组前三位又恰好是高段位的“赌神”“赌侠”“赌圣”，可解释当前人选高度重复的问题（`apps/server/src/competitive-bots.ts`、`apps/server/src/matchmaking-service.ts`）。
- 当前 10 个预置机器人中后 7 个段位均为黑铁Ⅴ（`rankLevel: 0`），前三个分别为较高段位；若严格按现有匹配范围，机器人候选必须结合等待时间和队伍成员段位动态计算。
- 用户 session、竞技档案、排队项、比赛与房间快照均已由 SQLite 持久化；好友关系和邀请可沿用同一数据库所有权和事务边界。
- 服务端已有 session presence，可作为在线状态权威来源；客户端已有头像资料弹窗，可扩展玩家 ID 和好友操作而无需新建第二套资料卡。

## Requirements

### R1 统一排位入口与房间流程

- 主页将“单人排位”和“组队排位”合并为一个“排位赛”入口。
- 点击“排位赛”后进入排位房间。
- 玩家可独自开始匹配，也可邀请好友或等待好友加入后组队开始。
- 房间需要清晰展示队伍成员、空位、邀请入口、准备或匹配状态。
- “允许机器人补位”从主页移动到统一排位房，由房主在开始匹配前勾选；该选择对整队生效。
- 非房主队员需要点击准备；房主不再单独准备，点击“开始匹配”即代表房主已准备。
- 单人房主可以直接开始；组队时只有所有非房主队员已准备，房主才能开始。

### R2 体验版机器人匹配与补位

- 组队排位人数不足时允许匹配预置机器人，保证体验阶段能够开局。
- 房间内沿用现有“允许机器人补位”勾选项，不提供一键立即开始的独立机器人排位按钮。
- 未勾选时只匹配真人，人数不足则继续等待。
- 勾选后仍先等待真人；沿用当前 5 秒体验期聚合窗口，窗口结束后用机器人补满四席。
- 10 个预置机器人都应按正常段位匹配逻辑进入候选池，不能固定只匹配“赌侠”“赌圣”“赌王”。
- 机器人兼容范围严格沿用真人匹配的等待扩展规则：10/20/40 秒逐步放宽，40 秒后不限段位。
- 5 秒聚合窗口结束后仅在当前段位范围内机器人数量足够时补位；否则继续等待到范围扩大。
- 同一兼容范围内优先选择近期使用较少的空闲机器人，不能按预置数组固定顺序截取，且整队不能被拆分。

### R3 玩家 ID

- 为现有用户和新用户初始化稳定、唯一、可展示、可搜索的玩家 ID。
- 玩家 ID 为 `1000-9999` 范围内的 4 位纯数字，由系统自动分配，永久不可修改。
- 预置机器人不占用可搜索玩家 ID，不能通过好友系统添加。
- 现有真人用户在数据库迁移时补齐 ID；新用户创建或首次完成微信绑定时获得 ID。
- 点击玩家头像时展示玩家 ID。
- 当前用户在主页可以查看和复制自己的玩家 ID。

### R4 好友申请与关系

- 匹配对局后，玩家可点击其他真人玩家头像发起好友申请。
- 接收方可以接受或拒绝好友申请。
- 主页好友管理支持输入玩家 ID 搜索并发起好友申请。
- 重复申请、添加自己、目标不存在、已经是好友等情况需要明确反馈。
- 好友申请不自动过期，直到接收方接受或拒绝，或申请方主动撤回。
- 同一方向的重复申请合并为同一条待处理记录。

### R5 好友管理与邀请

- 主页可打开好友管理。
- 好友列表展示在线或离线状态。
- 好友管理支持删除已有好友；二次确认后双向解除好友关系，历史比赛数据不变。
- 在线好友可被邀请进入当前排位房间。
- 好友邀请需要有接收、拒绝、失效和房间不可加入等反馈。
- 房间邀请最多保留 10 分钟；房间关闭、开始匹配、满员或变为不可加入时立即失效。
- 好友申请与房间邀请只通过游戏内通知交付：在线时实时到达，离线后重新进入小程序可查看待处理记录。
- 本期不接入微信订阅消息、模板消息或微信会话发送。

### R6 主页视觉优化

- 缩小现有大按钮，重新组织主要与次要入口。
- 排位入口保持最高视觉优先级，好友管理、个人信息及其他模式作为次级操作。
- 不改变现有品牌识别和核心玩法文案。
- 页面需要适配微信小程序常见手机尺寸，并提供可访问的点击热区、禁用态、加载态、空态和错误态。

### R7 客户端范围

- 本次好友、统一排位房和主页改版只在微信小程序端完整实现。
- Web 端不新增对应界面，但共享协议与服务端改动不得破坏 Web 端现有房间、排位和玩家资料功能。

## Acceptance Criteria

- [x] AC1：主页只有一个主要“排位赛”入口，点击后先进入排位房；单人房主可直接开始，组队时所有非房主队员准备后由房主开始。
- [x] AC2：排位房未勾选机器人时只匹配真人；勾选后保留 5 秒聚合窗口，并按 10/20/40 秒段位范围在机器人足够时补满四席。
- [x] AC3：自动化测试证明 10 个预置机器人均可在符合段位条件时进入候选结果，连续对局不会固定只取数组前三名，且真人队伍不被拆分。
- [x] AC4：每个微信绑定真人拥有 `1000-9999` 内稳定且唯一的玩家 ID，服务重启后不变化；预置机器人没有可搜索 ID。
- [x] AC5：主页和真人头像资料均展示玩家 ID；点击非自己真人头像可发起好友申请，机器人没有该操作。
- [x] AC6：可通过完整 4 位玩家 ID 精确搜索并发起申请；接收方可接受或拒绝，申请方可撤回，重复申请不生成多条待处理记录。
- [x] AC7：好友管理展示在线状态并支持二次确认后双向删除；删除不改变历史比赛数据。
- [x] AC8：在线好友可收到游戏内排位房邀请并接受或拒绝；接受成功后进入房间，10 分钟或房间不可加入后邀请失效。
- [x] AC9：好友申请、好友关系和待处理邀请在刷新、重新登录或服务重启后仍可恢复；实时提示不包含其他玩家的私有社交数据。
- [x] AC10：非法、越权或冲突操作返回稳定错误码，小程序展示可理解且归属正确的中文反馈。
- [ ] AC11：小程序主页、排位房和好友管理在横屏目标尺寸及安全区下无横向溢出，主要按钮不再纵向占据整屏，并具备 loading、empty、error 和 disabled 状态。
- [x] AC12：Web 不新增好友界面，但全仓类型检查、测试和构建通过；现有对局、重连、结算、段位和退出流程无回归。

## Out of Scope

- 好友聊天、朋友圈、赠礼、黑名单和好友分组。
- 微信订阅消息、模板消息、客服消息或微信会话分享好友申请。
- 跨服务器或跨环境查找用户。
- 机器人学习型 AI 或全新出牌策略。
- 对品牌 Logo、游戏规则和段位体系进行重做。
